Frame Header Fields

Every byte of the 64-byte header that precedes each frame on the USB 3 pipe — what it is, why it exists, and how to read it without getting a plausible wrong answer.

existing 32 B (format 3) new 32 B (format 4) magic / resync reserved

Existing block — bytes 0–31 · unchanged in format 4

MAGICbyte 0 · 4 Bexisting

"SLI0" for a video frame, "SLI1" for a control reply. Stored as 0x30494C53; little-endian, so the bytes on the wire read 53 4C 49 30.

Why it exists: control replies share this pipe with frames. Without a discriminator the host would parse a reply as the start of an image.

frame_idxbyte 4 · 4 Bexisting

Free-running 32-bit counter, +1 per emitted frame, cleared only by reset. 414 days at 120 fps, so it never wraps in practice.

Why it exists: stream continuity. If it advances by more than one between packets, a frame was lost in transit. That is its whole job.

Do not expect it to restart. It is deliberately not zeroed by the epoch reset and not reset per scan — if it were, a frame dropped at a scan boundary would be indistinguishable from a legitimate restart, and boundaries are where drops are most likely. Scan-relative position is slot, below.
NCOL · NROWbyte 8 · 2 B + 2 Bexisting

Frame geometry in pixels — columns then rows.

ldrop · nf_run · slotbyte 12 · 4 Bexisting

ldrop (18 bits) counts frames that arrived short and were padded. nf_run is how many frames this burst actually captured; slot is this frame's position within it.

Why it is in the header: so a bad frame can be attributed to a real drop rather than guessed at. A run of frames with a static ldrop is positive proof nothing was lost during it.

Static is the healthy reading, not zero. A non-zero but unchanging ldrop means drops happened earlier and none are happening now. Compare consecutive frames, don't test against zero.
FBYTES · FBYTES/4byte 16 · 4 B + 4 Bexisting

Payload length in bytes and in 32-bit words. 1,638,400 bytes for a full frame at 10 bpp packed.

Why both: the pipe moves whole words, and the header states the padded length, so a host can consume exactly what is on the wire.

formatbyte 24 · 4 Bexisting

How the payload is packed, and which header version follows.

210-bit right-aligned in 16-bit words (legacy)
3dense packed 10-bit — 4 pixels in 5 bytes · 32-byte header
4as 3, plus the 32-byte extended block described below
Switch on this. Never assume it. The source says why: reading packed bytes as u16 "will produce a convincing-looking wrong image" — it does not fail, it just quietly gives you the wrong picture.
~MAGICbyte 28 · 4 Bexisting

Bitwise inverse of MAGIC, closing the first block.

Why it exists: a host that loses its place in the stream can scan for the magic/inverse pair and resynchronise, rather than drifting and interpreting payload as a header.

Extended block — bytes 32–63 · format 4 only

vsync_seqbyte 32 · 4 Bnew

Which projected frame this exposure belonged to. Counts vsync edges of the video being sent to the projector. Zeroed by the epoch-reset command (opcode 8) on the next vsync.

Why it exists: triggers stack. With a delay longer than one frame, the capture of pattern k arrives while pattern k + floor(D/T) is on screen. This field states the pairing instead of making the host reconstruct it from a delay register and a frame period.

Across cameras: HDMI passes through each unit, so every camera in a daisy chain sees the same vsync. One broadcast reset gives them all a common epoch — no clock distribution needed.

Per-hop latency is real. Camera N sees the shared vsync slightly later than camera 1 — small and constant, but measure it before trusting cross-camera timestamps at fine resolution.
tick_in_framebyte 36 · 3 Bnew

Ticks of 10 ns since that frame's vsync. 24 bits spans 167.8 ms, so it covers frame rates down to about 6 Hz.

Together with vsync_seq this is the timestamp: vsync_seq × frame_period + tick_in_frame. Same units as gl_dly and the vsync period, so nothing needs converting.

pattern_idxbyte 39 · 1 Bnew

{frq[1:0], fra[2:0]} — which SLI pattern was displayed. fra is the phase step 0–7.

frq = 0coarse — ×1, about one period across the field
frq = 1mid — ×6
frq = 2fine — ×36
frq = 3not a fringe — flat full-field flashing block, for texture/albedo

Why it is separate from vsync_seq: that says which projected frame; this says what was on it. They differ whenever a pattern is held across more than one frame.

exposurebyte 40 · 2 Bnew

Integration time as used for this frame, in 375 ns units. 1600 → 600 µs.

Why per-frame: exposure is settable at runtime over the Ft+ (opcode 1). A frame captured before a change must not be interpreted with the value read after it.

gl_dlybyte 42 · 3 Bnew

The vsync→trigger delay in effect when this frame was captured, in 10 ns ticks. 0–167 ms.

What it is for: pixels do not reach the screen when their vsync goes out — the projector adds latency, and a DLP with sequential RGB LEDs has real gaps between colours. This delay places the exposure deliberately inside the projected frame.

trig_outbyte 45 · 1 Bnew

How many triggers were outstanding when this one was issued — effectively ceil(delay / frame period).

Why it is here: it is the pairing offset in flight. Redundant if vsync_seq and pattern_idx are both present — which is the argument for having all three, since each can check the others.

hflagsbyte 46 · 1 Bnew
epoch_validan epoch reset has been applied since power-up
gl_engenlock was commanded on
gl_livevsync was actually arriving
orient0 = fringes vary down rows · 1 = across columns

gl_en and gl_live are deliberately separate. They differ exactly when the display has gone away and the trigger has fallen back to free-running — the state most worth being able to see in the data.

orient is required to interpret pat_period. The period applies to rows or to columns depending on it; without it the phase map cannot be reconstructed.
hdr_verbyte 47 · 1 Bnew

Version of this second block. Currently 1.

Why not just use format: format describes the payload packing, which is what a host must switch on to decode pixels. hdr_ver describes the metadata, so the reserved bytes can be filled in later without touching payload semantics.

pat_periodbyte 48 · 2 Bnew

The fringe period in pixels, for this frame. 0 when frq = 3, which is a flat flashing field and has no period.

Why the period and not just the frequency index: frq is an index, and the real period is solved per display mode at runtime:

F = active size along the varying axis · b = ceil(F/288) · P_lo = 288b, P_mid = 48b, P_hi = 8b (exact 1 : 6 : 36)

So the same frq = 1 is a different spatial frequency at every resolution. Deriving it host-side needs orient, a replicated ceil division, and the assumption that neither changed mid-scan.

The period is re-solved on a display mode change. A scan spanning one silently changes fringe period. Carrying it per frame is what makes that visible instead of corrupting a phase map that still looks plausible.
reservedbyte 50 · 10 Bnew

Zero. Held for measured trigger→integration delay and achieved integration length per frame, the projected mode and refresh, capture-time health flags, ROI id, and a payload CRC.

~MAGICbyte 60 · 4 Bnew

Closes the extended block, so it can be validated independently of the first 32 bytes.

64 bytes total against a 1,638,400-byte payload — 0.004%. Design detail and rationale in FRAME_HEADER_PLAN.md.
